# Frontend UI Engineering

## Overview

Build production-quality user interfaces that are accessible, performant, and visually polished. The goal is UI that looks like it was built by a design-aware engineer at a top company — not like it was generated by an AI. This means real design system adherence, proper accessibility, thoughtful interaction patterns, and no generic "AI aesthetic."

## Key rules applied to this project

- Avoid the AI aesthetic: no purple-everything, no excessive gradients, no rounded-everything, no stock card grids, no shadow-heavy design. Flat/subtle, purpose-driven layouts, consistent spacing scale, semantic color tokens.
- Typography hierarchy: h1 page title (one per page) → h2 sections → h3 subsections → body → small. Never skip levels.
- Color: semantic tokens, 4.5:1 contrast for normal text, never color-alone to convey state (pair with icon/text labels — our congestion pills do this).
- Accessibility (WCAG 2.1 AA): keyboard-reachable controls, visible focus, labeled form controls, `role="status"`/`aria-live` for dynamic updates, meaningful loading/error/empty states (never blank screens).
- Responsive mobile-first; test 320px / 768px / 1024px / 1440px.
- Loading: skeleton states for content (not spinners); optimistic updates where safe.
- State ownership: simplest approach that works; explicit transitions; no prop drilling past 3 levels.

## Verification (after UI changes)

- [ ] Renders without console errors
- [ ] All interactive elements keyboard accessible (Tab through)
- [ ] Screen reader conveys content structure (landmarks, headings, live regions)
- [ ] Responsive at 320 / 768 / 1024 / 1440px
- [ ] Loading, error, and empty states all handled
- [ ] Follows project design tokens (spacing, colors, typography)
- [ ] No axe-core / devtools accessibility warnings

## Red flags

- Missing error/loading/empty states; blank screens on fetch failure
- Color as sole state indicator; generic AI look; inline arbitrary pixel values
- No keyboard testing; focus lost on dynamic updates
